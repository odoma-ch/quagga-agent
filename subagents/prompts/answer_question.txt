## SPARQL Best Practices & Issues
- Avoid full table scans: Never use ?s ?p ?o - always bind at least one term (subject, predicate, or object). This applies even with filters - FILTER on an unbound triple pattern is still a full scan.
- Always use LIMITs: Apply LIMIT during exploration (e.g., LIMIT 10 or LIMIT 50) to ensure fast feedback. Use OFFSET in combination with LIMIT for pagination, but be aware that large OFFSET values can be inefficient.
- Declare ALL prefixes: Always (PREFIX)_DECLARE every namespace used, including rdf:, rdfs:, xsd:, skos:. Never use prefixed terms without declaration.
- Valid sub-string matching syntax: Use `FILTER(CONTAINS(LCASE(STR(?var)), "text"))` or `FILTER(REGEX(STR(?var), "text", "i"))`. Never write `?var CONTAINS "text"`, `LCASE(?var) CONTAINS ...`, or use SQL-style `LIKE`.
- Valid equality checks: Use FILTER(?var IN (<iri1>, <iri2>)) or VALUES, not ?var = <IRI> in WHERE patterns.
- Filter literals inclusively: Handle string identifiers with varying datatypes using UNION patterns.
- Aggregation rules: Non-aggregated variables must appear in GROUP BY exactly as selected; use HAVING for aggregate filters, not FILTER.
- Prefer VALUES over UNION: Use VALUES for many literals/IRIs to avoid HTTP 431; split large queries into smaller ones.
- Entity resolution: First resolve named entities to URIs using string matching for discovery, then bind those URIs directly - don't use string filters as URI substitutes.
- One-hop diagnostics: After query failures, inspect specific predicates with one-hop queries like ?s <predicate> ?mid LIMIT 20 before broad exploration.
- Validate joins incrementally: If a 3-4+ join query times out or returns empty, test each hop separately before reassembling the full query; do not add aggregation until the join path is verified.
- Date/time filtering strategy: Prefer typed ranges when the datatype is confirmed (e.g., bounded date filters). If date values are heterogeneous/untyped, use explicit year candidates with `VALUES` (or equivalent bounded buckets) instead of broad `CONTAINS(STR(?date), "...")` filters on large joins.
- Count only after a selective query works: First get rows with the final join/filter pattern, then convert to `COUNT(DISTINCT ?entity)`; do not run broad count queries on unverified or timeout-prone filters.
- Prefix safety check (required): Before sending a query, verify every prefix used in the query body is declared in `PREFIX` statements (`xsd:`, `rdf:`, `rdfs:`, `skos:` etc.). If not, add declarations before execution.
- Timeout recovery rule: If a query times out, do not rerun near-identical variants. Reduce join width first (drop OPTIONAL/extra patterns), preselect candidates in a subquery with `LIMIT`, then add one constraint back at a time.
- Avoid global keyword scans on massive predicates: For `FILTER(CONTAINS(...))` over high-cardinality fields (titles, labels, names), first anchor by a known class, graph slice, year bucket, or candidate subquery; do not combine unconstrained text scan + date join in the first attempt.
- Subject-heading pivot for keyword trends: If title/name keyword queries fail but matching subject concepts are found, resolve the subject URI(s) first, then count works linked to those URI(s). Prefer exact URI matching; do not use URI substring filters like `CONTAINS(STR(?subject), "...")` as a final query strategy.
- Predicate discovery before broad `?p`: If you must use `?work ?p <subjectURI>`, first run a tiny diagnostic query to identify concrete predicate(s), then switch to those predicate IRIs in aggregation queries.

## Important: Use UNION pattern for literal values
DOI literal values (and other string identifiers) may include an explicit `^^xsd:string` datatype annotation in some triples. To ensure compatibility with both old and new data, match both plain literals and typed literals using a UNION pattern. For example:
```sparql
{
  ?identifier literal:hasLiteralValue "10.1038/nature12373" .
}
UNION
{
  ?identifier literal:hasLiteralValue "10.1038/nature12373"^^xsd:string .
}
```
Apply this pattern whenever matching string literal values such as DOIs, ORCIDs, or other identifiers.
